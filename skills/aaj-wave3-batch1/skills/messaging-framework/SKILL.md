# Messaging Framework

Organize everything you say into one core message and a few proof-backed pillars — so the whole team tells the same story, in the buyer's language.

## When to use this
- Messaging is inconsistent across the site, deck, and sales calls.
- There's a value prop but no structure beneath it.
- A launch, rebrand, or new segment needs a message map the team can work from.

## When not to use this
- Positioning isn't settled → run `positioning-statement` first; messaging is downstream of it.
- The user just needs the single hero line → use `value-proposition`.

## What you need
Pull from `brand-product-context`: the positioning, the value proposition, the ICP/segments, the differentiator, the proof, and the voice. If the positioning or value prop is a `(gap)`, close it first.

## Method
1. **Start from positioning and the value prop** — the framework organizes them; it doesn't reinvent them.
2. **Write one core message** — the single thing every buyer should walk away believing. If there are two, you don't have one yet.
3. **Build 3–4 pillars** — the few themes that support the core message. Fewer, sharper pillars beat a long list.
4. **Back each pillar with proof** — a metric, an outcome, a mechanism. A pillar without proof is a claim.
5. **Write the "say this" lines** for each pillar — the actual sentences the team can use, in the brand's voice.
6. **Create audience variants** — same pillars, different emphasis and language by segment or persona.
7. **Pressure-test** — would the buyer recognize their own words; could a competitor claim the same pillars? Sharpen until both pass.

## Output
- **Core message** — one sentence.
- **Pillars (3–4)** — each with: the claim, the proof behind it, and 1–2 "say this" lines.
- **Audience variants** — the emphasis/language shift per segment.
- **Off-message** — what *not* to say (claims you can't back, or that blur the positioning).

## Defensibility check
Confirm there's exactly one core message, every pillar carries real proof, the lines use the buyer's language (not internal jargon), and a competitor couldn't claim the same set. A pillar without proof or a second "core" message is the usual failure — fix it before delivering.
